# GB200 micro-batch size 对 GEMM 效率的影响

结论：**mbs 该不该大于 1，取决于序列长度，且分界点在 1k 附近。** 把 mbs 从 1 提高到 8：

| 序列 | 整迭代 GEMM 吞吐变化（27B / 2.4T） | 机理 |
| --- | --- | --- |
| 256 | **+58% / +62%** | 每个 GEMM 只有几十 µs，被固定发射开销与 CTA 数量不足主导 |
| 1k | **+13% / +15%** | 固定开销仍占 ~10%，但已接近饱和 |
| 4k | −3% / −12% | 收益与损失互相抵消，L2 尚可承受，主要被降频吃掉 |
| 16k | −15% / −9% | L2 溢出与功率墙降频同时生效，几乎全线下降 |

所以"mbs = 1 已经喂饱 GB200"这个判断**在小序列下不成立**，它是 seq ≥ 4k 才出现的现象。
短序列下 mbs=1 的瓶颈不是 tensor core 算力，而是每次 kernel launch 之间的空隙：
seq256 时单个 GEMM 的纯计算时间只有 8–30 µs，与发射开销同量级。

- 被测模型：Qwen3.8 27B（dense）、Qwen3.8 2.4T（MoE）
- 硬件：单张 NVIDIA GB200（152 SM），BF16，TP = CP = 1，无通信
- 测试框架：`examples/gb200/micro-batch-size/`，scope `GEMM`
- 原始数据：`results/gb200/micro-batch-size/`，`seq256` / `seq1k` / `seq4k` / `seq16k`

测量的是训练实际使用的 Megatron 模块与 kernel。计时在 CUDA 闸门下完成，屏蔽 CPU 开销，
不使用 CUDA Graph。`fwdbwd` 包含 dgrad 与 wgrad。无通信争抢，因此结果是单卡计算时间的
**上界**。

测试框架的设计前提是"输入 tensor 常驻 L2" —— 这个前提只在 `m` 较小（seq ≤ 1k）时成立，
seq16k 下输入远超 L2，本身就是被测量的机制之一（见 §3.3）。

## 1. 两个模型的 GEMM 操作

`m` 是 token 行数（= `sequence_length × mbs`，grouped case 为本地各 expert 行数之和），
`k` 是输入特征数，`n` 是输出特征数。层数取自各模型 README，`次数` 为单次训练迭代
（含 MTP 层）中该 GEMM 的出现次数。

## 2. 测试结果

### 2.1 整迭代 GEMM 吞吐（按出现次数加权，TFLOP/s）

用各层单次耗时 × 出现次数求和，得到一次训练迭代中 GEMM 部分的合并吞吐。加粗为该序列的

**最优 mbs 随序列长度单调左移：256/1k → 8，4k → 2–4，16k → 1**（`fwdbwd` 下整条曲线再
左移一格：1k → 4，4k 与 16k → 1）。两个模型、四个序列共八个组合，全部落在这一条线上，
没有例外。

注意 seq256 的 `fwdbwd` 幅度（+150~154%）远大于 `fwd`（+58~62%）。原因很直接：nsys 记录
显示每个 GEMM 在 `fwd` 下只发射 1 个 kernel，在 `fwdbwd` 下发射 3 个（fwd + dgrad +
wgrad）。发射开销占总时间的比例因此翻了近三倍，摊薄它的收益也就更大。

  L2 溢出是随 case 时长渐进的，不是开关。
- **`output_layer` 与 `shared_expert_gate` 是两个不跟随趋势的例外**：
  - `output_layer` 在 **seq1k 就开始下降**，峰值从 mbs=8 退到 mbs=1。两个模型共 20 个
    case 中**只有它在 seq1k 就转跌**（27B −11%，2.4T −17%），其余最早也要到 4k 才开始
    转跌（27B 的 `mlp_fc1`，2.4T 的 `attention_*` / `gdn_*` / `routed_expert_fc1`），
    多数要到 16k。原因见下。

    `n = 1` 本质是 reduction），列出来只为说明它在 mbs=1 时有多么没被利用。

`output_layer` 是唯一在 seq256 下仍上涨、在 seq1k 下就翻为下降的 case。原因是它不缺并行度：
`n = 248320` 本身就能铺满 SM，所以 mbs=1 时它已经跑到 1325（256）/ 1674（1k）TFLOP/s，
远高于同期其他 case 的 850–900。抬 mbs 对它几乎没有补 SM 的收益，反而在 seq1k 下因为
`m` 增大之后的访存压力（权重矩阵 5120 × 248320 × 2 B ≈ 2.5 GB 需反复读）而下降。

### 2.4 退化 case 的绝对量级（说明为何可忽略）

`router_gating` 与 `shared_expert_gate` 在四个序列下都上涨，但绝对量级极小。

数值仍为 mbs = 1 / 2 / 4 / 8（`fwd`，TFLOP/s）：

| case | k × n | 256 | 1k | 4k | 16k | 单次 FLOPs | 整迭代占比 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `router_gating` | 8192 × 512 | 161 / 262 / 516 / 823 | 521 / 814 / 1158 / 1316 | 1159 / 1338 / 1347 / 1416 | 1359 / 1385 / 1504 / 1500 | 0.1–0.8 G | 0.4% |
| `shared_expert_gate` | 8192 × 1 | 0 / 1 / 1 / 3 | 1 / 3 / 4 / 5 | 4 / 5 / 5 / 6 | 5 / 6 / 6 / 7 | 0.2–6.4 G | < 0.01% |

`n = 512` / `n = 1` 的窄 GEMM 在 mbs=1 时 SM 占用率极低，抬 m 确实在填 SM，但绝对收益
很小：`router_gating` 整迭代占比只有 0.4%，`shared_expert_gate` 不到 0.01%。
**这两个 case 不应作为优化目标。** 短序列下它们涨得猛只是因为起点太低（`router_gating`
在 seq256/mbs1 只有 161 TFLOP/s），不代表整迭代有对应的收益。

### 2.5 短序列为什么反过来：固定发射开销

seq256 与 seq1k 下的反常趋势不是功率墙造成的 —— 这两个序列**全程没有掉频**：

| 序列 | 27B m1 时钟 | 27B m8 时钟 | 2.4T m1 时钟 | 2.4T m8 时钟 |
| --- | --- | --- | --- | --- |
| 256 | 2062 MHz | 2062 MHz | 2062 MHz | 2062 MHz |
| 1k | 2062 MHz | 2062 MHz | 2062 MHz | 2062 MHz |
| 4k | 2062 MHz | 2017 MHz | 2062 MHz | **1301 MHz** |
| 16k | 2062 MHz | **1256 MHz** | 2062 MHz | **1252 MHz** |

短序列的绝大多数 case 都 < 3 ms、功耗只有 230–310 W（对比 seq16k/mbs8 的 461–586 W），
离板级功率墙很远。这里的瓶颈是**每个 kernel 的固定成本**。

把单次耗时对 FLOPs 做线性拟合 `t = t₀ + c·FLOPs`，在 seq256 上得到 `t₀ ≈ 20 µs`、
渐进效率 ≈ 1750 TFLOP/s。同一个拟合在 seq16k 上会给出**负的 `t₀`**（−200 ~ −470 µs），
因为长序列是被降频而非发射开销支配的 —— 这正好说明两个序列区间由两套不同的机制主导。

20 µs 的固定成本对 seq256/mbs1 是致命的：除 `output_layer` 外，各 case 的实测单次耗时
只有 19–85 µs，与固定开销同量级 —— 其中 `attention_linear_proj` 与 `gdn_out_proj`
只有 18.7 / 18.8 µs，几乎整个 kernel 时间都被固定开销占满。用"m8 耗时 ÷ 8"估算无开销
耗时，与 m1 实测的差值就是发射开销：

| 模型 | 序列 | Σ(m1 耗时) | Σ(m8 耗时 / 8) | 多余开销 |
| --- | --- | --- | --- | --- |
| 27B | 256 | 0.786 ms | 0.547 ms | **+0.239 ms（+44%）** |
| 2.4T | 256 | 1.571 ms | 1.180 ms | **+0.391 ms（+33%）** |
| 27B | 1k | 2.334 ms | 2.439 ms | −0.105 ms（−4%） |
| 2.4T | 1k | 4.504 ms | 4.747 ms | −0.243 ms（−5%） |

seq256 下 mbs=1 有三分之一到近一半的时间花在等待 kernel 起来，而不是算 FLOPs；
seq1k 下这笔开销已经摊薄到 5% 以内，所以 1k 的涨幅（+13~15%）远小于 256（+58~62%）。

同一现象的第二个侧面是 **CTA 数量**。cuBLAS 选出的 kernel 配置在 mbs=1 时 `m` 只有
256 行，能铺到 152 个 SM 上的 CTA 极少：

| case（2.4T seq256） | mbs=1 选中 kernel | mbs=8 选中 kernel |
| --- | --- | --- |
| `attention_linear_proj` | `128x128_64x8_2x2_2cta` | `256x256_64x4_2x2_2cta` |
| `routed_expert_fc1` | `128x80_64x10_2x2_2cta` | `128x192_64x7_2x1_2cta` |
| `router_gating` | `64x32_64x16_2x2_2cta` **splitK** | `128x64_64x10_2x2_2cta` |
| `shared_expert_gate` | `32x64_64x16_4x1` **splitK** | `64x8_64x16_4x1` |

mbs=1 时 cuBLAS 被迫选小 tile，并在最窄的 case 上启用 splitK 来人为造出并行度；
mbs=8 后 `m = 2048`，同一组 GEMM 才能挑到大 tile 的 kernel。这也是为什么短序列下
"抬 mbs" 真的在补 SM 利用率 —— 与 seq ≥ 4k 的情况正好相反。

> 注：seq1k 的 `output_layer` 在 mbs=8 时反而从 1723 掉到 1433。它是唯一 `n`
> 极大（248320）的 case，`m` 小时靠 `n` 方向就已经铺满 SM，`m` 增大只增加了访存压力。

## 3. 为什么 seq ≥ 4k 时 mbs = 1 已经喂饱了 GB200

本节解释 §2 中长序列（4k / 16k）那一半的趋势。短序列的机制见 §2.5 —— 两者是相反方向
的两套限制，分界点在 1k 附近。

### 3.1 mbs=1 时 GPU 已在 boost 满频

这是长序列结论的根基。`sm_clock_mhz`（case 结束时的采样值）显示，mbs=1 时各序列、各
case 都躺在 2062 MHz 的 boost 频率上，无论 mbs 取多少：

| case | k × n | mbs=1 时钟 | mbs=8 时钟 |
| --- | --- | --- | --- |
| 27B `attention_linear_proj` | 6144 × 5120 | 2062 | 2062 |
| 27B `mlp_fc2` | 17408 × 5120 | 2062 | 2062 |
| 27B `mtp_eh_proj` | 10240 × 5120 | 2062 | 2062 |
| 2.4T `gdn_out_proj` | 16384 × 8192 | 2062 | **1305** |
| 2.4T `router_gating` | 8192 × 512 | 2062 | 2062 |

mbs=1、seq=4k 时 `m` 已有 4096 行，**tensor core 已经满载**，所以抬 mbs 换不到 GEMM
效率，只会把 case 时长从 <1 ms 拖到几十 ms，进而触发降频。注意这个"已经满载"的说法
在 seq256（`m` = 256 行）下并不成立 —— 那正是 §2.5 的发射开销区间。

### 3.2 机制一：功率墙降频

case 时长与采样到的时钟严格相关：

按 case 时长分桶，统计两个模型、四个序列的全部 768 条记录（取各序列/模型的跨度）。
短序列只填满前两个桶：

| case 时长 | 平均 `sm_clock_mhz` | 平均功耗 | 主要出现在 |
| --- | --- | --- | --- |
| < 1 ms | **2062**（boost） | 231–393 W | 全部序列 |
| 1–3 ms | 1863–2035 | 272–318 W | 全部序列 |
| 3–10 ms | 1277–1634 | 328–399 W | seq ≥ 1k |
| 10–50 ms | 1214–1309 | 454–631 W | seq ≥ 4k |
| > 50 ms | **1194–1237** | **1138–1210 W** | seq ≥ 4k |

这张表同时说明了为什么短序列不受降频影响：seq256 下 57/64（27B）与 80/96（2.4T）
条记录落在 < 1 ms 桶，全部停在 2062 MHz；而 > 50 ms 的降频桶在 seq256 下是空的，
在 seq1k 下也只有 1 条。

算力上界：152 SM × 4 tensor core × 4096 FLOP/cycle（BF16 dense）× 2.062 GHz ≈ **2567 TFLOP/s**。
实测值 1419–1604 对应的是 **~1250–1350 MHz** 的稳态频率，正好等于实测采样到的时钟区间。
`output_layer` 在 27B seq4k 各 mbs 下功耗恒定在 1084–1174 W、时钟 1155–1305 MHz，是撞了
板级功率上限的直接证据。

**所以 1500 TFLOP/s 不是 GEMM 实现不好，是这卡在持续负载下只能跑到 ~1300 MHz。** 由此也
导致 `tflops` 列不能跨 case 比较：短 case 采样到 boost、长 case 采样到稳态，两者混在一起。

### 3.3 机制二：L2 溢出

测试框架的设计前提是"输入常驻 L2"。这个前提只在 m 较小时成立：

| 配置 | 单 case 输入张量 | 与 L2 的关系 |
| --- | --- | --- |
| 27B seq256 mbs8 | 5120 × 2048 × 2 B ≈ 21 MB | 可常驻 L2 |
| 27B seq1k mbs8 | 5120 × 8192 × 2 B ≈ 84 MB | 仍可承受 |
| 27B seq4k mbs1 | 5120 × 4096 × 2 B ≈ 42 MB | 可常驻 L2 |
| 27B seq4k mbs8 | 5120 × 32768 × 2 B ≈ 336 MB | 开始溢出 |
| 27B seq16k mbs1 | 5120 × 16384 × 2 B ≈ 168 MB | 临界 |
| 27B seq16k mbs8 | 5120 × 131072 × 2 B ≈ 1.3 GB | 远超 L2 |
| 2.4T seq16k mbs8 | 8192 × 131072 × 2 B ≈ 2.1 GB | 远超 L2 |

`m` 增大后激活读取转为从 HBM 取，权重读的摊薄收益被抵消。这解释了为什么最吃激活读取的
case 退化最严重：27B seq16k 的 `mlp_fc2` 掉 19%、`gdn_in_proj` 掉 13%，2.4T seq16k 的
`routed_expert_fc2` 掉 20%，而权重占比高、激活占比低的 case（`output_layer`）只掉
3.5–4%。

### 3.4 三个机制的分工

按序列长度，主导机制依次切换：

- **seq256**：单 case 输入 ≤ 34 MB，L2 完全装得下，时钟全程 boost、功耗 < 310 W。
  唯一的问题是**每个 kernel 只有几十 µs、CTA 数量不足**（§2.5），所以 mbs 增大是纯收益。
- **seq1k**：发射开销已摊薄（< 5%），L2 仍不吃紧，降频尚未发生。此时抬 mbs 的收益来自
  更大的 tile 选择空间，净收益 +13~15%，已接近饱和。
- **seq4k**：单 case 输入进入几百 MB，L2 开始溢出；同时 `m` 足够大使得长 case 触发
  **降频**。两个机制一正一负，所以表现为有涨有跌。
- **seq16k**：L2 溢出与降频**同时生效**，所以几乎全线下降，且降幅最大（`mlp_fc2`
  −19%、`routed_expert_fc2` −20%）。

**一句话总结**：mbs 的最优点由"发射开销 / SM 占用"与"降频 / L2 溢出"这两组力量的相对
强度决定，前者在短序列占优、后者在长序列占优，交叉点落在 1k–4k 之间。

## 4. 结论与适用范围

1. **mbs 的最优点取决于序列长度，不是常数。** 256 / 1k → mbs=8，4k → mbs 2–4，
   16k → mbs=1。两个模型、`fwd` 与 `fwdbwd` 四种组合的趋势完全一致。

   | 序列 | `fwd` 推荐 | `fwdbwd` 推荐 | 相对 mbs=1 的整迭代 GEMM 吞吐（27B / 2.4T） |
   | --- | --- | --- | --- |
   | 256 | 8 | 8 | +58% / +62%（`fwdbwd` 下 +154% / +150%） |
   | 1k | 8 | 4 | +13% / +15%（`fwdbwd` 下 +20% / +19%） |
   | 4k | 2–4 | 1 | +2% / +2%（拐点，收益已接近于零） |
   | 16k | 1 | 1 | 基准（更大 mbs 净损失 4–15%） |

2. **短序列下 mbs 是有效的 GEMM 效率旋钮。** 与长序列相反，seq256/1k 下增大 mbs 确实
   提升 GEMM 吞吐，因为瓶颈是 kernel 发射开销与 CTA 数量，而不是 tensor core 算力。
3. **长序列下不要用 mbs 换 GEMM 效率。** seq ≥ 4k 时增大 mbs 只引入降频与 L2 溢出两项
   损失。
4. **`router_gating` / `shared_expert_gate` 的低 TFLOP/s 不是问题。** N=512 / N=1 的窄
   GEMM 在逐 kernel 归因里会以"低效 kernel"跳出来（seq256/mbs1 时 `router_gating` 只有
   161 TFLOP/s），但整迭代占比分别只有 0.4% 与 < 0.01%。

**适用范围 —— 以下三点必须同时成立，结论才适用：**

- 只适用于**孤立模块的单卡 GEMM**。这份数据是单卡计算时间的上界，不含通信。
- 覆盖 **seq 256 / 1k / 4k / 16k**，即 `m` 从 256 到 131072 行。更长序列时 `output_layer`
  会第一个 OOM、第一个撞功率墙（27B seq4k mbs8 的 `output_layer` 峰值已达 44.5 GiB）。
  更短序列（`m` < 256）时发射开销占比会继续上升，mbs 的收益只会更大，但本数据未覆盖。
- **不能用来论证"训练时 mbs 不能大"。** 真实训练里抬 mbs 的价值不在 GEMM 效率，而在
  通信与计算的重叠窗口变长、optimizer step 频率下降、DP/EP allreduce 摊薄。评估 mbs
  收益要看端到端 step time 或通信重叠率。**这条与 §4.2 的关系是**：长序列下 GEMM 侧
  反对增大 mbs，此时端到端的取舍才成为主要问题；短序列下 GEMM 侧本身就支持增大 mbs。

### 4.1 若要进一步验证

1. **锁频重测**：用 `nvidia-smi -lgc 1300` 固定 SM 频率后重跑，消除时钟变量，mbs 的纯
   几何效应会直接暴露。
2. **分离 L2 与 m 两个因素**：构造超出 L2 但 m 不变的输入尺寸，即可把当前混在
   seq16k/mbs8 一列里的两个机制拆开。
3. **定位交叉点**：补测 seq 1.5k / 2k / 3k，把推荐 mbs 从 8 翻到 1 的临界序列长度
   收窄到具体区间。
4. **验证发射开销假设**：在 seq256 下用 CUDA Graph 包住同一组 GEMM 重测 —— 如果 mbs=1
   的劣势消失，就证明它来自 kernel 发射而非算力。

### 4.2 对调优的实际含义

- **小序列 / 小 `m` 场景（预训练早期、SFT 短样本、RL rollout 的短 prompt）**：mbs 越大
  越好，直到撞上显存。GEMM 侧没有理由坚持 mbs=1。
- **长序列场景（≥ 4k）**：mbs=1 在 GEMM 侧是最优的，增大 mbs 的动机只能来自端到端
  step time（通信重叠窗口、collective 摊薄），不能用 GEMM 吞吐来论证。
