# RL 训练侧 Offload 背景

## 1. 问题背景

在 RL 训练系统中，rollout 和训练通常以交替方式运行：rollout 负责生成一批新的轨迹或样本，训练侧消费这批数据并完成一次或多次参数更新。一个 RL 迭代的整体周期受较慢的一侧决定，因此两侧耗时不匹配会直接转化为设备空闲和资源浪费。

当前观察到的典型情况是：

- rollout 生成一批训练数据约需要 **15 分钟**；
- 训练侧消费这批数据约 **5 分钟**即可完成；
- 训练侧完成后，需要等待下一批 rollout 数据，训练资源在剩余时间内处于空闲状态。

因此，当前瓶颈并不只是单次训练的吞吐，而是 rollout 与训练之间的流水线平衡。若训练侧能够在等待期间释放一部分 GPU 资源，系统就可以用更少的训练资源维持相同的 RL 迭代节奏。

## 2. 大模型场景下的资源矛盾

训练超大模型时，模型参数、梯度、优化器状态和激活值共同构成了很高的显存需求。为了让模型能够放入设备，训练通常需要提高 pipeline parallelism（PP）值，将模型切分到更多 GPU 上。

但是，较大的 PP 会带来两个直接后果：

1. **训练占用的 GPU 数量增加。** 即使训练计算本身只需要较短时间，也必须为整个训练阶段保留完整的并行组。
2. **训练侧聚合的算力过大。** 训练集群规模由“模型能否放下”决定，而不是由“训练是否需要持续占满这些 GPU”决定，导致训练和 rollout 的资源规模及时间都难以匹配。

这使得 RL 系统出现一种结构性浪费：为了容纳模型而配置了大规模训练并行组，但训练计算很快完成，随后大量 GPU 等待 rollout。

## 3. 具体规模示例

以 **2.4T 参数模型**为例，为了完成训练可能需要：

- **144 个 4-GPU 的 GB200 节点/实例**；
- 合计 **576 张 GPU**。

在这个规模下，即使训练侧只运行 5 分钟，也需要为整个训练阶段预留 576 张 GPU。若 rollout 仍需要 15 分钟生成下一批数据，训练侧的大量 GPU 时间就无法被有效利用，整体系统的有效利用率受到明显限制。

## 4. 训练侧 Offload 方案的动机

为缓解上述矛盾，希望引入一种面向 RL 训练侧的 offload 方案：在不改变 RL 算法语义的前提下，将训练阶段暂时不参与当前计算的数据从 GPU 移出，并在需要时恢复到 GPU。候选对象包括：

- 模型参数或参数分片；
- 优化器状态；
- 梯度及其分片；
- 跨层或跨 micro-batch 保存的激活值；
- 其他可以在训练阶段按需重建或搬运的临时状态。

这里的“卸载”重点是降低训练侧的 GPU 常驻容量，使模型不必完全依赖很大的 PP 规模来容纳。卸载介质可以是 CPU 内存或其他可用的分层存储，具体选择需要结合带宽、容量、同步方式和实现复杂度评估。

## 5. 目标与权衡

该方案的首要目标不是让训练单步更快，而是让训练侧的资源占用和 rollout 的生产节奏相匹配：

- **降低训练侧 GPU 数量或显存占用**，释放更多 GPU 用于 rollout 或其他任务；
- **允许训练时间适度变长**，将训练耗时从约 5 分钟延长到接近 rollout 的 15 分钟；
- **减少两阶段之间的等待**，使 RL 迭代周期主要由有效工作构成；
- **保持训练结果一致性**，offload 不应改变梯度、参数更新和 checkpoint 的语义；
- **提供可调的速度-资源权衡**，根据 rollout 时延、GPU 规模和 CPU/互联带宽选择 offload 比例及粒度。

理想状态是：训练侧即使因为参数、激活值或优化器状态搬运而变慢，也能在下一批 rollout 数据到达前完成训练。这样可以用更少的训练 GPU 覆盖同样的 RL 迭代周期，并提升整个 RL 系统的资源利用率。

## 6. 后续需要回答的问题

围绕这一方案，后续设计需要进一步明确：

- 哪些状态最适合 offload，以及它们的容量、访问频率和搬运带宽要求；
- 如何在 PP、TP、DP 及可能的 FSDP 组合下组织参数、梯度和激活值的生命周期；
- 如何通过预取、双缓冲和计算/通信重叠隐藏搬运开销；
- 如何在 rollout 等待窗口内动态选择 offload 比例，使训练耗时接近目标周期；
- 如何验证 offload 对数值一致性、故障恢复、checkpoint 和 RL 收敛的影响；
- 当 CPU 内存、PCIe/NVLink 或节点间带宽成为瓶颈时，系统如何降级或调整并行配置。
